Краткое описание проекта: [docs/project.md](docs/project.md).
Команды, архитектурные ограничения, БД, проверка и релиз: [docs/development.md](docs/development.md).
Решения для БД и диагностических команд: [ADR 0001](docs/adr/0001-immutable-sessions.md), [ADR 0002](docs/adr/0002-diagnostics-interface.md).
Карта поиска: [REPO_MAP.md](REPO_MAP.md). Термины и границы показателей: [CONTEXT.md](CONTEXT.md). Слои и данные: [docs/architecture.md](docs/architecture.md).

- Сначала исследуй публичную границу изменения и существующие тесты.
- API начинается в `api/openapi.yaml`. Сгенерированные Go и TypeScript файлы не редактируют вручную; используй `make generate`.
- Не ослабляй существующие тесты. Проверяй наблюдаемое поведение через HTTP, DOM или публичную команду.
- Используй существующие команды Makefile и самое узкое достаточное подтверждение во время работы.
- В учебной задаче о liveness достаточно `make generate PNPM=pnpm` и тестов пакета `backend/internal/adapters/httpapi`. Полную `make verify-fast` в этом прогоне не запускай: это отдельный этап evaluator и release, а не требование к каждому небольшому изменению.
- Не добавляй зависимости без необходимости. Сохраняй границы application, adapters и platform.
- Работай только с учебной копией. Реальная БД и пользовательские данные не входят в эту задачу.
- В окружении оценки Docker недоступен агенту; контейнерные проверки выполняет независимый проверяющий после окончания ответа. Не выдавай их за запущенные тобой.
- Заканчивай перечислением изменений, фактически выполненных проверок и оставшихся ограничений.
- Для аналитического вопроса сначала различи данные, доменные определения и технические решения. При неполном покрытии не выдавай известную часть за полную сумму и не заменяй неизвестное нулём.
